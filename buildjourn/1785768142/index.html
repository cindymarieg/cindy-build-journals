What this automation does

This is the publishing engine behind every Build Journal you'll ever generate. Whenever you (or the skill on your behalf) finish documenting a project, this system takes that write-up and turns it into a real, permanent, shareable web page — automatically, with nothing to click or upload by hand.

In plain terms: you save a build journal → a few seconds later, a live link exists for it. That link never changes, so you can bookmark it, send it to someone, or come back to it months later to remember exactly how something was built.

Pipeline flow

1
A new build journal is written to Airtable. Whether it's the skill or a direct call, all the details — project name, status, the actual document content — land in a single new Airtable record in one go.
2
Airtable notices the new record and reacts automatically. The moment that record is created, an automation built into the base fires — no one has to click anything.
3
A quiet signal gets sent to Make.com. Airtable's automation runs a tiny script whose only job is to say "hey, record X is ready" to a private web address (a webhook) that Make is listening on.
4
Make fetches the full document and ships it to GitHub. It reads back everything in that Airtable record, then places the actual HTML file into your GitHub repository — this is the moment the content physically leaves Airtable.
5
Netlify notices the new file and publishes it. Within about a minute, the page is live at its own permanent web address — done, with zero further action from you.
6
The master index quietly updates itself too. The same Make run that published the page also adds it to a running list, so it shows up automatically on the browsable index of every journal ever published — no separate step, no extra trigger.
7
If a step fails, you get a heads-up instead of silence. A Slack message lands in a dedicated channel the moment the Airtable fetch or the GitHub push fails — so a broken pipeline gets noticed in minutes, not days.

Airtable base Data store

This is the filing cabinet everything starts in. Every build journal — regardless of which project it documents — becomes one row here first, before anything gets published anywhere else.

Base: Build Journal, table Project Documents. Holds the project name, whether it's a "Build Journal" or "How-To Guide," whether the work is complete or still in progress, the date, and the actual document content itself.

Make scenario — "Update Build Journal" Writer

This is the intake step — the thing that actually creates the Airtable record in the first place. Think of it as the front desk: everything comes through here first.

Called directly by Claude via a Make MCP tool. Takes five pieces of information and creates one new Airtable record with all of them filled in at once — nothing is added piecemeal afterward.

Airtable automation — "Publish Journals" Trigger

This is the automatic handoff — the piece that notices "something new just got saved" and kicks the rest of the pipeline into motion without anyone lifting a finger.

Watches the Project Documents table for brand-new rows. The instant one appears, it runs a tiny script that tells Make.com the record's ID, so Make knows exactly what to go fetch and publish.

Make scenario — "Upload Build Journal to Netlify via Github" Publisher

This is the actual publisher. It's the piece that takes something sitting privately in Airtable and turns it into a real, public web page.

Listens for the signal from Airtable, pulls the full record's contents, then hands the document off to GitHub as a new file — which is what ultimately makes Netlify publish it.

GitHub repo Storage

This is simply where the finished web pages live, permanently, so Netlify has something to serve.

github.com/cindymarieg/cindy-build-journals — public (required for Netlify's free tier), holds one folder per build journal ever published.

Netlify site Publish target

This is what actually makes the finished page visible to a browser — the "hosting" layer.

cindy-build-journals.netlify.app — watches the GitHub repo and re-publishes automatically the instant anything new is pushed to it. No manual deploy step, ever.

Build Journals index Browse view

This solves the "I published a bunch of pages but have no way to find them again" problem. It's a single home page listing every journal ever published, searchable and filterable.

A static, branded page (index.html) that reads a small data file (journals.json) at load time and renders a searchable, filterable list. The publishing scenario appends one entry to that data file every time a journal successfully goes live — using Make's native code module to safely fetch, update, and re-save the file's contents on GitHub without ever overwriting someone else's concurrent write.

Slack failure alerts Safety net

This is the "someone tell me if this breaks" piece. Without it, a broken pipeline just goes quiet — no new journals appear, with no obvious reason why, until you happen to notice.

Attached to the two steps most likely to fail (the Airtable fetch and the GitHub push) inside the publishing scenario. On failure, it posts a warning to the #build-journal-alerts Slack channel, then deliberately re-raises the error so Make's own 3-strikes auto-deactivation still kicks in normally — the alert adds visibility, it doesn't paper over the failure.

What It Does

Publishes any build journal you save into a permanent, shareable web page — automatically, with no manual publishing step.

Trigger

Saying "save the build journal," "journal this," "document what we built," or similar to Claude — or any new record being created in the Project Documents Airtable table.

Usage Steps

1
At the end of (or during) a build session, tell Claude to save the build journal.
2
Answer the three quick questions: project name, complete or in progress, and whether you want a How-To Guide.
3
Review the list of components Claude found — correct anything that's wrong before it generates the document.
4
Preview the generated document, then confirm you're ready to publish.
5
Wait about 30–60 seconds, then the live link is ready.

Expected Output

A live page at cindy-build-journals.netlify.app/[project-slug]/[timestamp]/, and that same page now also appears automatically on the index at cindy-build-journals.netlify.app. A new Airtable record also exists as the permanent internal record of what was written.

Troubleshooting

Nothing published, no error shown: Check the Make scenario "Upload Build Journal to Netlify via Github" isn't deactivated — Make automatically turns it off after 3 failed runs in a row.
Editing an existing record instead of creating a new one: Won't trigger publishing. The automation only fires on brand-new records — always let the skill create a fresh one rather than editing an old one.
Got a Slack alert about a failure: Check #build-journal-alerts for the specifics, then reactivate the Make scenario "Upload Build Journal to Netlify via Github" — it auto-deactivates after 3 failed runs in a row.

Known Fragile Points

• The GitHub file path is based on when a record was created, not last edited — re-publishing the same record will fail with a conflict.

• Having the Make scenario open in a browser tab while changes are made elsewhere can silently revert those changes on autosave.

Script sent an empty payload to Make (case-sensitivity)
The Airtable script's input variable was named RecordID, but the script referenced input.config().recordId — lowercase mismatch. Since input.config() keys are case-sensitive, this returned undefined, producing an empty request body. Fix: match the reference exactly to the variable's declared name.
Webhook received data but couldn't map it ("Bundle: Empty")
Make's custom webhook module needs its data structure explicitly taught. Fix: open the Webhook module → "Detect new values" → send one real test request while listening → Save.
Automation never fired on real skill runs
The original trigger was "record updated, watching html_content." Real runs write html_content at creation time, not as a later edit — so that trigger never fired. Fixed by switching to "record created."
GitHub 422 "Unprocessable Entity" on re-publish
Re-editing an already-published record retries the same file path and GitHub rejects the overwrite. Doesn't affect normal use, since real runs always create new records.
Make's conditional expression syntax broke a reusable tool's JSON body
A one-off GitHub-push tool used {{if(...)}} to optionally include a file's SHA only when updating an existing file. The resulting JSON was malformed and every call failed with "not valid JSON." Editing the tool afterward also failed silently (Internal Server Error) rather than surfacing the actual problem. Fix: built a second, simpler tool that always requires the SHA — avoids the conditional entirely rather than debugging Make's IML string-building blind.
Stale webhook queue kept resurfacing old errors
Repeated manual tests left several old, broken requests sitting in Make's webhook queue. Every reactivation reprocessed them alongside real new tests, making failures hard to distinguish from progress. Fix: Make → open the scenario → Diagram → click the Webhook module → its queue view lets you select and delete stale items directly, separate from clearing execution history.
Slack alerts failed with "channel_not_found" across 5 separate connection attempts
Cindy has two Slack workspaces with confusingly similar names: the-brave-pivot.slack.com (the real one, used day-to-day) and thebravepivot.slack.com (an older one, still actively used by 3 other automations). Every OAuth authorization attempt — including incognito windows and manually switching active workspace first — kept landing on the old workspace regardless, and even a brand-new dedicated channel created specifically for this still came back "channel not found." That ruled out a simple default-workspace theory: the Make Slack app had apparently never been authorized into the real workspace at all. Fix: on the actual Slack OAuth consent screen (not Make's UI, not the Slack client), there's a "Workspace" dropdown — explicitly selecting "The Brave Pivot" there finally produced a connection with the correct team ID. Four prior attempts never surfaced that picker; the fifth did.
